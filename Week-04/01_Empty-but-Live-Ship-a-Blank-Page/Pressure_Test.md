# Pressure Test

After comparing the three options, I pressure-tested the choices against my actual timeline, portfolio requirements, and ability to maintain the site.

## 1. What breaks if I choose the simplest option?

If I choose the No-Code option, I can launch quickly, but I lose an important opportunity to demonstrate my technical skills.

My portfolio is meant to showcase Backend Development, Web Development, and AI work. A no-code portfolio would show that my projects exist, but it would not show that I can build and understand a website myself.

It could also become limiting when I want highly customized layouts for detailed case studies, technical content, screenshots, or project filtering.

**Conclusion:** No-Code is easy to maintain, but it does not prove enough of the skills I want my portfolio to represent.

---

## 2. What would I maintain if I chose the most powerful option?

React would give me reusable components and better scalability, but it would also introduce more things to maintain:

* React dependencies
* npm/build tooling
* Components and routing
* Deployment/build errors
* Framework-related debugging

React would be useful if my portfolio became much larger or required more interactive features. However, my current portfolio does not need that level of complexity.

**Conclusion:** React is powerful, but I would be maintaining complexity that I do not currently need.

---

## 3. Can I finish in two weeks?

Yes.

I already have project content, case studies, screenshots, GitHub repositories, and other portfolio material. Therefore, I am not starting the content creation from zero.

With plain HTML, CSS, and JavaScript, I can focus my time on structuring, designing, testing, and deploying the portfolio instead of spending most of the time learning a new framework.

**Conclusion:** The chosen stack is realistic for my two-week timeline.

---

## 4. Does it show my work the way it needs to be shown?

Yes.

The portfolio needs to display:

* Project screenshots
* Detailed case studies
* Technical skills
* GitHub repositories
* Live demo links
* Internship/project experience
* About information
* Contact links

HTML, CSS, and JavaScript can handle all of these requirements without requiring a backend.

I can create project cards, image galleries, case-study sections, responsive layouts, navigation, and small interactive features using the chosen stack.

**Conclusion:** It meets the actual presentation needs of my portfolio.

---

## 5. Can I maintain this myself?

**Yes.**

This is one of the main reasons I chose plain HTML, CSS, and JavaScript.

I will not need to manage a framework or a large dependency tree. I can open the files directly, understand the code, update project information, change styling, and push the changes to GitHub.

There will be some manual work when adding projects or updating repeated sections, but that is manageable for my current project count.

---

## 6. Final Pressure-Test Result

| Question                               | Result                                                   |
| -------------------------------------- | -------------------------------------------------------- |
| Does No-Code become limiting?          | Yes — mainly for technical credibility and customization |
| Does React add maintenance?            | Yes — tooling, dependencies, and framework complexity    |
| Can I finish in two weeks?             | **Yes**                                                  |
| Does HTML/CSS/JS display my work well? | **Yes**                                                  |
| Can I maintain it myself?              | **Yes**                                                  |
| Is a backend needed at launch?         | **No**                                                   |

### Decision

After pressure-testing the options, I am choosing **Plain HTML + CSS + JavaScript hosted on GitHub Pages**.

It gives me the best balance between technical credibility, simplicity, maintainability, and the actual needs of my portfolio.
